# i18n & RTL

FlowBoard ships **English (`en`)** and **Arabic (`ar`, Modern Standard)**. Arabic
is right-to-left, so this is a _direction_ feature as much as a translation
feature: the whole shell mirrors, and the language is stamped on `<html>` before
React mounts so nothing paints the wrong way round.

Read this before you write a user-facing string, before you write a margin, and
before you "fix" a `dir="ltr"` you did not expect. §11 is the recipe; §6 and §7
are the two enforcement contracts a reviewer checks.

## 1. The two layers, and which one owns what

| Layer               | File                              | Owns                                                                                                                                           |
| ------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Language policy** | `apps/web/src/lib/lang-policy.ts` | The preference (`fb-lang-v1`), the browser default, `<html lang\|dir>`, `isRTL()`, `getIntlLocale()`, the subscription. **No i18next import.** |
| **i18n runtime**    | `apps/web/src/i18n/index.ts`      | The i18next instance, the catalogs, the lazy Arabic load, `changeLanguage`. **Depends on the policy.**                                         |

**The dependency runs one way only: `i18n` → `lang-policy`, never back.** The
policy answers "which language / which direction" synchronously, from
`localStorage`, with no library loaded — which is what lets `main.tsx` stamp the
document before the Arabic chunk has even been requested, and what lets a layout
component ask `isRTL()` without dragging i18next into its import graph. Importing
i18next from the policy would invert that and make every module that only wants
to know which way the page runs pay for the whole library.

### 1.1 The exported contract

```ts
export type Lang = 'en' | 'ar';
export const LANG_STORAGE_KEY = 'fb-lang-v1';

getLangPref(): Lang               // stored, else browser-detected
isRTL(): boolean                  // `ar` today; the one place the question is answered
getIntlLocale(): string           // 'en-US' | 'ar-u-nu-latn'
intlLocaleFor(lang: string): string   // the same rule as a PURE function
setLangPref(next: Lang): void     // persist + restamp <html lang|dir> + notify
subscribeLang(cb): () => void
useLang(): Lang                   // useSyncExternalStore over the above
initLangPolicy(): void            // pre-paint stamp; called from main.tsx
```

- **First-visit default follows the browser.** A `navigator.language` whose
  primary subtag is `ar` starts Arabic; everything else — including a missing
  `navigator` in node tests — starts English.
- **`intlLocaleFor(lang)` exists because the rule was being re-spelled by hand.**
  `components/tasks/task-dates.ts` inlined `lang === 'ar' ? 'ar-u-nu-latn' : lang`
  three times before WP3.8, which quietly produced `en` rather than `en-US`. A
  formatter that already holds a `lang` from `useLang()` must derive its tag from
  **that value**, not re-read the store, or a formatter memoized on `lang` can be
  built from a newer preference than the one it is keyed to.
- **Nothing outside this module reads `navigator.language` or writes
  `<html lang|dir>`.** `isRTL()` has exactly one non-test caller
  (`components/diagnostics/DiagnosticsDrawer.tsx`); everything else subscribes
  through `useLang()`.
- **Two places write the preference:** the Topbar's language menu
  (`components/layout/Topbar.tsx` → `chooseLang`) and `pages/ProfilePage.tsx`,
  which calls `setLangPref(user.locale)` on save — the account locale is the
  durable preference, and saving it without applying it would leave the page in a
  language the user just said they did not want.

### 1.2 Boot order — `apps/web/src/main.tsx`

`bootstrap()` is `async` for exactly one reason: the Arabic catalog is a dynamic
import, and rendering before it lands would paint an English frame and then swap
every string on screen.

```
import '@/stores/useThemeStore'   // side effect: tokens + `dark` on <html> at MODULE SCOPE
  → initLangPolicy()              // SYNC: <html lang|dir> is correct NOW
  → initFaviconUpdater()
  → await initI18n(getLangPref()) // the only await before render, wrapped in try/catch
  → createRoot(#root).render(<StrictMode><AppProviders><RouterProvider/></…>)
```

**The `dir` stamp must precede the React mount, and it must not depend on the
i18n step.** It is synchronous and reads `localStorage` directly, so an Arabic
session is already right-to-left while the Arabic chunk is still in flight — and
_stays_ so if that chunk never arrives. Hence the swallowing `try/catch`:
`bootstrap()` is fire-and-forget, so an escaping rejection would mean
`root.render` never runs and the page stays blank. English is bundled and is the
`fallbackLng`, so a failed Arabic fetch degrades to English copy in a correctly
mirrored frame, and `loadArabic` un-memoizes the rejection so the next language
switch can retry.

## 2. The catalogs

```
apps/web/src/locales/
  en/  admin analytics auth backlog board calendar common diagnostics errors
       notifications orgs palette reports roadmap settings table tasks theme
       validation workflow
       index.ts     ← aggregates all 20 namespaces, `as const`
  ar/  … the identical 20-file tree
```

### 2.1 TypeScript modules, not JSON

`apps/web/src/i18n/i18next.d.ts` declares:

```ts
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    resources: typeof en;
    returnNull: false;
  }
}
```

**English is the key-shape authority.** `t('common:actions.save')` is checked at
compile time; `t('common:actions.saev')` is a build error; a namespace added to
`locales/en/index.ts` is usable from `t('<ns>:…')` immediately. Arabic is never
typed against — it may lag, and every missing key falls through to
`fallbackLng: 'en'`. **Arabic must therefore never introduce a key English does
not have**: nothing could ever reach it, and §4.2's parity test rejects it.

Two consequences agents trip on:

- **`as const` on every catalog default export is load-bearing.** Widening a
  namespace to `Record<string, string>` erases the literal key union and silently
  turns every `t()` call in the app into an unchecked one.
- **`i18next.d.ts` is ambient augmentation only.** It imports `typeof en` as a
  _type_ and must never gain a runtime import.

### 2.2 English bundled, Arabic lazy

`apps/web/src/i18n/index.ts` creates one default instance **synchronously at
import** — importing the module is enough to get a usable English instance, which
is what unit tests rely on and why `initI18n()` is only needed where Arabic might
be the _starting_ language.

| Concern         | How                                                                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| English         | Static `import en from '@/locales/en'`, passed as `resources: { en }`. It is the `fallbackLng`, so it must precede the first `t()`.                           |
| Arabic          | `import('@/locales/ar')`, registered namespace-by-namespace with `addResourceBundle('ar', ns, bundle, false, false)`.                                         |
| Fetched once    | Memoized in `arabicLoad`; a **rejected** promise clears the memo so a transient blip can be retried.                                                          |
| Race safety     | `applyLang` re-checks `getLangPref() !== lang` **after** the await — a fast en→ar→en toggle must not commit a stale language.                                 |
| Staying in step | `subscribeLang(...)` is registered at **module scope**, not inside `initI18n`, so importing the module keeps the instance following the policy even in tests. |
| `NAMESPACES`    | `Object.keys(en)` — derived from the catalog so the list and the tree cannot drift.                                                                           |
| `escapeValue`   | `false`. React escapes what it renders; escaping first would print `&#39;` for an apostrophe in a display name.                                               |
| `returnNull`    | `false`. A missing key renders the key, not `null` into a `ReactNode` slot — and `i18n/errors.ts` depends on that (§10.2).                                    |

`locales/en/index.ts` and `locales/ar/index.ts` are **stitch files**: they import
each namespace and export the object. Adding a namespace means editing both, and
both are integration-owned rather than view-owned.

### 2.4 Key conventions

- **camelCase, `page.section.element`** — `workflow:statuses.deleteTitle`.
- **Prefix every key with its namespace and pass namespaces as an ARRAY:**
  `const { t } = useTranslation(['board', 'common']);` then `t('board:title')`.
  `i18next.d.ts` declares `defaultNS: 'common'`, so a bare `useTranslation()`
  types only _unprefixed_ `common` keys and `t('board:title')` will not compile.
  The one string-form call in the app is `useTranslation('validation')` inside
  `components/ui/form.tsx` — it resolves bare `validation` keys and nothing else,
  which is exactly what `localizeValidationMessage` hands it.
- **Interpolation is `{{name}}`**, with `escapeValue: false`.
- **Never concatenate translated fragments.** Word order differs; one key, one
  sentence, interpolation for the variables. There is **no `<Trans>` usage
  anywhere in this codebase** — if you need one, you are adding a convention.
- **Brand names never translate.** `brand: 'FlowBoard'` is byte-identical in both
  catalogs, and `locales/ar/common.ts` bans the transliteration «فلوبورد» outright.

### 2.5 Typed-literal key config modules

Several modules are **data about the UI** rather than UI: a nav model, a metric
registry, a preset gallery. They must not call `t()` — that would be the
module-scope trap in §11.1 — so they store the **key** and the render site
resolves it. The convention is a module-local key type, so a typo or a renamed
catalog entry is a compile error rather than a raw key rendered in a topbar.

| Module                                                                | Key type                                                 | Fields                                                                      |
| --------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| `components/navigation/nav.config.ts`                                 | `NavLabelKey`, `NavSectionKey` — **hand-written unions** | `NavItem.labelKey`, `NavSection.labelKey`                                   |
| `components/navigation/breadcrumb-trail.ts`                           | `CrumbLabelKey` (extends `NavLabelKey`)                  | `KeyCrumb.labelKey`, the closed `SEGMENT_LABEL_KEYS` map                    |
| `components/palette/palette-items.ts`                                 | reuses `NavLabelKey`                                     | its own `palette:` section headings                                         |
| `components/admin/analytics/metric-catalog.ts` → `metric-registry.ts` | `AnalyticsKey` — **derived**                             | `titleKey`, `subtitleKey`, `headerKey`, `labelKey`, and three `Record` maps |
| `components/theme/theme-presets.ts`                                   | `ColorPresetKey`, `FontPresetKey`, `DimensionOptionKey`  | `labelKey` on every preset and dimension option                             |

**Two techniques, and the difference is deliberate.** `nav.config.ts` writes its
union by hand; the analytics registry **derives** it from the catalog:

```ts
type LeafPath<T> = {
  [K in keyof T & string]: T[K] extends string ? K : `${K}.${LeafPath<T[K]>}`;
}[keyof T & string];

export type AnalyticsKey = `analytics:${LeafPath<typeof enAnalytics>}`;
```

`LeafPath` recurses over an `as const` catalog and terminates on
`T[K] extends string`, so it produces the union of every dotted leaf —
`'metrics.work.cycle-time.title'` and the rest. This is why **`as const` on every
catalog is load-bearing** (§2.1): widen one to `Record<string, string>` and this
type collapses to `string`.

Derived is the better default for a catalog you own end to end: renaming a key
breaks the registry at compile time with no list to maintain. The hand-written
form survives where the module names keys from **several** namespaces
(`common:nav.*`, `palette:*`) and a derived union would have to be a union of
unions for no gain.

**The derived union is a type only; Arabic is still checked at runtime.**
English is the shape authority and Arabic is never typed against, so
`metric-registry.test.ts` resolves every key the registry emits against **both**
catalogs. A registry entry with an English key and no Arabic twin compiles
cleanly and fails there.

`metric-catalog.ts` also exports `MetricTitleKey` and `metricTitleKey(domain,
metric)` — the dependency-free half, so `breadcrumb-trail.ts` can name a metric
without importing the HTTP client. It guards with `Object.hasOwn`, never a plain
index, because both segments come off a URL and
`…/analytics/traffic/toString` would otherwise resolve a prototype member. The
registry's one deliberate borrow across namespaces is typed too, as
`AdminReuseKey`:

```ts
export type AdminReuseKey = 'admin:units.ms' | `admin:eventType.${TelemetryEventType}`;
```

## 3. The Arabic glossary — BINDING

There is no separate glossary file. **The glossary lives in the header docblock
of `apps/web/src/locales/ar/common.ts`**, and every other `locales/ar/*.ts`
header points back at it. It exists because a single term was being translated
three different ways in three namespaces (`label` as تسمية / وسم / تصنيف;
`assignee` as المسؤول / المُسنَد إليه), which makes the product read as though
three people wrote it.

**Use these exactly. A new term is added to that header FIRST, then used.**

Three style rules apply to every Arabic file, from the same header:

1. **Digits are always Western** (`ar-u-nu-latn`, §9) — even inside running
   prose: «آخر 7 أيام», never «آخر ٧ أيام». Mixing «٧» in a sentence with «7» in
   the column beside it is worse than either alone.
2. **Punctuation is Arabic**: «،» «؛» «؟» — not `,` `;` `?`. The sole exception
   is the thousands separator inside a Western number.
3. **`FlowBoard` is a trademark and is never transliterated.**

Register is Modern Standard Arabic throughout — no dialect, and no transliterated
English where an Arabic word exists.

## 4. Plurals

### 4.1 The two CLDR sets

i18next resolves a plural key by appending a CLDR category suffix to the base
key. The two languages do not have the same categories:

| Language | Categories                                   | Suffixes a base MUST declare               |
| -------- | -------------------------------------------- | ------------------------------------------ |
| `en`     | `one`, `other`                               | exactly `_one` and `_other` — nothing else |
| `ar`     | `zero`, `one`, `two`, `few`, `many`, `other` | **all six**                                |

Worked example, `table:toolbar.exported` in `locales/{en,ar}/table.ts` — English
carries two entries (`exported_one`, `exported_other`); Arabic carries six
(`exported_zero` «لم تُصدَّر أي مهمة.» · `_one` «تم تصدير مهمة واحدة.» · `_two`
«تم تصدير مهمتين.» · `_few` · `_many` · `_other`).

The English catalog declares **eight** plural bases in total:
`calendar:grid.more`, `calendar:chip.points`, `orgs:picker.members`,
`orgs:picker.projects`, `orgs:invites.days`, `orgs:teams.members`,
`table:toolbar.exported`, `workflow:statuses.tasksHere`. Everything else counts
with a labelled figure instead — see §4.3.

**Never hand-roll `count === 1 ? … : …`.** It has no Arabic answer at all.

### 4.2 What the parity test asserts — and what it deliberately does not

`apps/web/src/i18n/locales.test.ts` flattens both catalogs to dotted leaf paths
and runs six assertions. Read this before you touch a plural key:

| Test                                                     | Asserts                                                                                                            |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `registers every namespace this wave added`              | `Object.keys(en)` contains `common, auth, validation, errors, orgs, settings, workflow`                            |
| `has the SAME namespace list in both catalogs`           | `Object.keys(ar).sort()` equals `Object.keys(en).sort()`                                                           |
| `<ns> has no key missing from Arabic`                    | Every English leaf **that is not a plural form** exists in Arabic                                                  |
| `<ns> has no key in Arabic that English lacks`           | Every Arabic leaf exists in English, **unless** it is another CLDR category of a base English declares as a plural |
| `<ns> declares exactly _one and _other in English`       | For every English plural base, the category set is exactly `{one, other}`                                          |
| `<ns> declares all six Arabic plural categories`         | For every **English** plural base, Arabic has all six suffixes                                                     |
| `leaves no English string sitting in the Arabic catalog` | Spot check over `errors, orgs, settings, workflow`: no identical value, modulo an allowlist                        |

**The asymmetry is the whole point.** The plain "no key missing from Arabic" test
filters plural keys out (`!pluralParts(key) && !arabic.has(key)`) — so it does
**not** assert that Arabic has `exported_one`. The sixth test does, and demands
**more**: all six categories, driven off the English base list. And the fourth
test does **not** flag `exported_two` as drift, because its base is an English
plural base. The exemption is narrow — an Arabic-only _non-plural_ key is still
drift, and so is an English plural base missing even one of Arabic's six.

Why it is written that way: a strict key-for-key diff pushes the catalogs into
exactly the wrong shape. Before WP5.1 the Arabic side carried a bare
`_one`/`_other` pair to satisfy the diff, i18next found no `_few` for `count: 3`,
and silently fell back to the **English** string inside an Arabic sentence —
"Exported 11 tasks." in a right-to-left toast. The parity test asserting that was
correct is the reason the bug survived.

The last test's `ALLOWED_IDENTICAL` allowlist is six entries, each justified:
`brand`, `language.english`, `language.arabic`, `createProject.keyPlaceholder`,
`profile.avatarPlaceholder`, `profile.namePlaceholder`. A project key is
uppercase ASCII in every locale, a URL is a URL, and a person's name is a proper
noun — transliterating the example produced a placeholder no Arabic reader would
ever type.

### 4.3 The namespaces that avoid plurals entirely

`board`, `backlog`, `roadmap` and `notifications` state in their headers that
they carry **no i18next plurals**, and render counts as a labelled figure
instead (`Subtasks: {{count}}`, `Cards: 12`). That reads the same at 1 and at 12
in both languages and both directions.

> Their headers still justify the choice as "an `_one`/`_other` pair would break
> catalog parity". That reasoning predates WP5.1 — the parity test now supports
> plurals properly (§4.2). The **policy** those files describe is still in force
> and their catalogs match it; only the stated reason is stale. Prefer a labelled
> figure in those four namespaces; use a proper six-form plural elsewhere.

## 5. RTL mechanics

### 5.1 `<html dir>` does the CSS; `Direction.Provider` does the behaviour

`lib/lang-policy.stamp()` sets `document.documentElement.lang` and `.dir`.
That one attribute drives every logical property, the `html[lang='ar']`
typography rule in `apps/web/src/index.css`, and the `rtl:` Tailwind variant.

`apps/web/src/AppProviders.tsx` mounts `<Direction.Provider dir={lang === 'ar' ? 'rtl' : 'ltr'}>`
**inside** `QueryClientProvider` and **outside** `TooltipProvider`, wrapping
`{children}`, `<PaletteMount/>`, `<Toaster/>` and the devtools.

**This is not redundant with `<html dir>`.** Radix primitives read direction from
_context_, not from the DOM, and default to `ltr` when no provider is mounted —
omit it and an Arabic session gets a correctly mirrored layout whose dropdowns,
selects and sliders still open and arrow-key the English way. The source is
`useLang()`, **not** `i18n.language`: the policy is the one synchronous,
subscribable answer, and it already stamped `<html dir>`, so the DOM and the
context can never disagree. `Direction` comes off the unified `radix-ui` package,
which is why no separate `@radix-ui/react-direction` dependency exists.

`components/ui/sonner.tsx` passes `dir` again to sonner's own `<Toaster>`, since
sonner is not a Radix primitive and does not read that context.

### 5.2 Logical Tailwind utilities — allowed and banned

**Never use `ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`, `text-left`,
`text-right`, `border-l`, `border-r`, `rounded-l`, `rounded-r`** — they do not
mirror, and a physical margin is the single most common RTL bug in this codebase.
Every one of them is mechanically greppable, which is exactly why §6 exists.

| Instead of                  | Use                           | Resolves to                      |
| --------------------------- | ----------------------------- | -------------------------------- |
| `ml-*` / `mr-*`             | `ms-*` / `me-*`               | `margin-inline-start` / `-end`   |
| `pl-*` / `pr-*`             | `ps-*` / `pe-*`               | `padding-inline-start` / `-end`  |
| `left-*` / `right-*`        | `start-*` / `end-*`           | `inset-inline-start` / `-end`    |
| `text-left` / `text-right`  | `text-start` / `text-end`     | `text-align: start` / `end`      |
| `border-l` / `border-r`     | `border-s` / `border-e`       | `border-inline-start` / `-end`   |
| `rounded-l-*`/`rounded-r-*` | `rounded-s-*` / `rounded-e-*` | inline-start / -end corner radii |
| `inset-x-*`, `top/bottom`   | unchanged                     | already direction-neutral        |

**`tailwind-merge` dedupes WITHIN a group, and logical and physical utilities are
DIFFERENT groups** (`apps/web/src/lib/utils.ts`). Mixing them _stacks_ both
instead of replacing one, so a call site overriding a primitive's `end-*` with
`right-*` gets both. That is one more reason the codebase is logical-only.

### 5.3 How `components/ui/*` handles direction

Most primitives need nothing — logical utilities plus Radix's own writing-mode
mirroring cover them (`card.tsx`, `scroll-area.tsx`, `calendar-layout.ts`,
`CalendarDayCell.tsx` all say so explicitly). The exceptions are **transforms and
animations, which CSS `direction` does not mirror**, so they are written with
`ltr:` / `rtl:` variants:

| File                                                                                                                                | Compensation                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `components/ui/switch.tsx`                                                                                                          | `rtl:data-[state=checked]:-translate-x-[calc(100%+2px)]`                   |
| `components/ui/sheet.tsx`                                                                                                           | `rtl:data-[state=open]:slide-in-from-right` / `…-left` per side            |

**The drawer's tablist is the one place direction is read from the DOM.** The
WAI-ARIA tabs pattern defines its arrow keys **physically**, and in a
right-to-left layout the tabs run end-to-start, so `ArrowRight` must move to the
_previous_ tab:

```ts
const forward = event.key === (isRtlDocument(asideRef.current) ? 'ArrowLeft' : 'ArrowRight');
```

`isRtlDocument()` reads `documentElement.dir` at keydown time rather than
subscribing to `useLang()`, so the keyboard semantics can never disagree with
the CSS-driven slide animation, which is gated on `:where(html[dir='rtl'])`.
This is a **behavioural** mirror, not a glyph one — do not "simplify" it into an
`rtl:rotate-180`.

**The last two rows are the same problem solved two different ways, and the
difference is worth understanding before you copy either.** `TablePagination`
mirrors its chevrons in CSS, because "previous page" there is purely a direction
of travel and `<html dir>` already knows which way that is; branching on the
language in the component would add a second source of truth next to the one the
document already provides. `CalendarToolbar` swaps the icon **component**,
because a page-wide `rtl:rotate-180` on that toolbar would also flip the chevron
inside any other control it hosts — and `ChevronLeft` is a glyph, not a layout,
so no logical CSS property turns it around. Prefer the CSS form; reach for the
component swap only when a blanket rotate would catch icons that must not move.

`components/ui/calendar.tsx` also passes DayPicker `dir={isArabic ? 'rtl' : undefined}`
plus the `arSA` date-fns locale, and its range caps are **logical**
(`rounded-s-*`/`rounded-e-*`): DayPicker lays the week out right-to-left under
`dir="rtl"`, so the row's `:first-child` and the range's earliest day land on the
same reading-start side.

## 7. LTR islands

An **LTR island** is a subtree that carries `dir="ltr"` inside an otherwise
mirrored page. There are three structural ones and one lexical one. The policy in
one sentence: **a mirrored timeline reads as time running backwards**, so the
coordinate space stays LTR while everything around it mirrors and every word in
it translates.

### 7.1 The Gantt canvas — `components/gantt/`

`GanttChart.tsx` puts `dir="ltr"` on the canvas pane; the sidebar next door
inherits the page direction. Everything downstream follows: `scrollLeft` counts
up from the left edge in every browser, `clientX` deltas mean what they say, and
`dateToX` needs no mirror. `GanttChart.test.tsx` pins it (`makes the canvas an
explicit dir="ltr" island and leaves the sidebar alone`).

**The split is LTR grid, RTL labels.** `GanttTimeAxis.tsx` is not translated in
_position_ but is fully translated in _words_: month names from `Intl` on
`getIntlLocale()`, the quarter from `t('roadmap:axis.quarter', …)`, and an
`sr-only` range sentence rather than 365 announced cells. `GanttSidebar.tsx`
mirrors completely — rows, disclosure arrows (`rtl:-scale-x-100`), task titles
(`dir="auto"`). `gantt-arrows.ts` notes that "right" and "left" are literal in
its geometry precisely _because_ it lives in the island.

### 7.2 The charts — `components/reports/`

`ChartFrame.tsx` is the single wrapper every Recharts plot lives in, carrying
`dir="ltr"`, `role="img"` and an `aria-label` holding the localized summary
sentence with its headline numbers. **Recharts does not mirror**: it computes
axis ticks, bar offsets, the tooltip cursor and the legend from a left-origin
cartesian model regardless of `direction`, so an RTL page gets a plot whose axis
labels are mirrored but whose data is not — the worst outcome, because it looks
deliberate.

**The boundary is tight, and two components exist to keep it tight:**

- `ChartLegend.tsx` is deliberately **HTML, not Recharts' `<Legend>`** — a legend
  trapped inside the SVG would run left-to-right with its swatches on the wrong
  side of the Arabic words. As page content it flips for free.
- `WorkloadBars.tsx` is **CSS, not Recharts**: a horizontal bar must grow from
  the reading start, so under Arabic it has to grow right-to-left. Logical
  properties do that automatically and the island exception disappears.

Everything else around a plot — card title, info tooltip, empty and error states,
the range picker, the toolbar — is normal page content and mirrors.

### 7.3 The diagnostics dock — `components/diagnostics/`

Not a `dir` island: the drawer's **dock sides** are physical (§6.1, §6.2) because
"dock it to the left" is a statement about the monitor, the way a developer moves
a console around. Its copy is fully translated, its timestamps are hand-padded
`HH:mm:ss.SSS` on purpose (a devtools column must be fixed-width, 24-hour and
millisecond-precise in every locale), and its flex order is computed by
`isDrawerFirst(dock, isRTL())` so a physical-left dock stays physically left.

### 7.4 Lexical islands — `dir="ltr"` on a span

Roughly 80 `dir="ltr"` attributes sit on individual spans, inputs and cells. They
are not layout decisions; they stop the bidi algorithm reordering a Latin run

## 8. `dir="auto"` — user-generated content

**Every span that renders text a user typed gets `dir="auto"`.** The attribute
gives the element the direction of its own first strong character, so an English
title inside an Arabic page reads left-to-right and an Arabic title inside an
English page reads right-to-left, both without the app knowing which.

The codebase uses **`dir="auto"` exclusively and has no `<bdi>` elements at all.**
`<bdi>` is an inline isolate; nearly every one of these sites is already a block
or a `truncate`d span that needs `dir` on itself, so a second wrapper would buy
nothing. Do not introduce one without a reason.

## 9. Digits and formatting

### 9.1 Western digits, always

`getIntlLocale()` returns `'ar-u-nu-latn'` for Arabic, so `1,234` never becomes
`١٬٢٣٤`. This is not a stylistic choice: task keys (`FLOW-142`), story points,
sprint numbers and dates are read side by side with Latin identifiers, and most
of the surfaces that show them — the table, the burndown axis, the Gantt time
axis — are `tabular-nums` grids where a digit swap breaks column alignment.
The Arabic glossary (§3, rule 1) extends the rule into running prose.

### 9.2 `apps/web/src/lib/format.ts` — the shared primitives

WP3.8 consolidated the helpers five views had each grown their own copy of.
Two rules everything in the file follows:

- **The locale is a PARAMETER, never read from the policy.** These are pure
  functions of their inputs, so a test can assert Arabic output with no language
  store and a caller can format two locales in one render. Callers apply
  `getIntlLocale()` (or `intlLocaleFor(lang)` when they already hold a `lang`).
- **A calendar day is a STRING, not a `Date`.** `YYYY-MM-DD` sorts
  lexicographically in chronological order, so comparisons need no parse, no
  timezone, and no chance of a due date flipping to overdue at 01:00 west of
  Greenwich. Every parse anchors at LOCAL midnight.

| Export                                 | Notes                                                                                   |
| -------------------------------------- | --------------------------------------------------------------------------------------- |
| `formatPoints(points, locale)`         | `maximumFractionDigits: 2` — halves render as `0.5`, `3` stays `3`                      |
| `toIsoDate`, `todayIso`, `fromIsoDate` | `fromIsoDate` **rejects an overflowing day** via a round-trip check (`2026-02-31`)      |
| `isOverdue(dueDate, today?)`           | A string comparison; null-tolerant                                                      |
| `formatIsoDate`, `formatDateTime`      | Cached `Intl.DateTimeFormat` per `(locale, options)`; return `''`, never `Invalid Date` |
| `relativeParts` / `formatRelative`     | Pure bucketing split from `Intl.RelativeTimeFormat(locale, { numeric: 'auto' })`        |
| `__clearFormatterCache()`              | Test seam — the cache is module-global and leaks across locale cases                    |

View-specific date math stays in its view (`board/board-meta.formatDueDate`,
`backlog/backlog-dates.formatDay`). The other locale-aware formatters —
`calendar/calendar-dates.ts`, `reports/chart-format.ts`, `gantt/gantt-format.ts`,
`admin/telemetry-format.ts` — are all built from `getIntlLocale()`.

### 9.3 What must never be hand-formatted

- **Never hand-write a date, month name, weekday or number separator.** They go
  through `Intl` on `getIntlLocale()`. `locales/en/calendar.ts` deliberately
  contains **no** weekday or month names for exactly this reason: translating
  them by hand would duplicate effort and drift from the `Intl` output the rest
  of the app uses.
- **Never interpolate a raw number into a summary string and expect i18next to
  format it.** `reports` and `admin` summaries interpolate values
  **pre-formatted** so i18next never reformats them.
- **Never localize a devtools timestamp.** `diag-chrome.formatLogTime` is
  hand-padded `HH:mm:ss.SSS` on purpose (§7.3).

## 10. The two translation seams

Some copy arrives from somewhere that cannot know about i18next. There are
exactly two such seams, and both translate at a **single render point**.

### 10.1 Validation — `apps/web/src/i18n/validation.ts`

Every FlowBoard form validates with the **same shared zod schema the API
validates with**. Those schemas attach English text from
`packages/shared/src/validation-messages.ts` (`VM_EMAIL_INVALID = 'Enter a valid
email address'`), and **that text is the wire contract** — a 422's
`error.details` carries it verbatim and the API's contract tests assert the exact
strings, so it cannot be an i18n key: `packages/shared` is runtime-neutral and
knows nothing about i18next. The translation therefore happens at the last
possible moment:

```ts
export const VALIDATION_MESSAGE_KEYS: Record<ValidationMessage, ValidationKey> = {
  [VALIDATION_MESSAGES.VM_REQUIRED]: 'required',
  … // 45 entries, keyed by the TEXT, because that is all a ZodIssue carries
};

export function localizeValidationMessage(t: TFunction<'validation'>, message: string): string;
```

`components/ui/form.tsx`'s `FormMessage` runs every message it is about to render
through it — one call site, so no form has to remember:

```tsx
const { t } = useTranslation('validation');
const body = error ? localizeValidationMessage(t, String(error.message ?? '')) : children;
```

**A form never translates its own field errors.** If you find a component calling
`t('validation:…')` for a field message, it is duplicating `FormMessage`.

Two guards, both required:

- **Compile:** the `Record<ValidationMessage, ValidationKey>` makes a new shared
  message a type error until it has a key, and `ValidationKey` is
  `keyof typeof enValidation`, so a renamed catalog entry breaks the map too.
- **Runtime:** `apps/web/src/i18n/validation.test.ts` asserts the map covers
  `VALIDATION_MESSAGES` exhaustively, that every mapped key resolves to real
  English copy (never the key echoed back — the failure the type cannot see), that
  the Arabic `validation` namespace has an entry per English key, and that an
  unmapped message passes through untouched.

Keep `locales/*/validation.ts` copy **field-agnostic**: one message is reused by
every schema that attaches it, so "Name cannot be empty" belongs there and "Enter
your project's name" does not.

### 10.2 API errors — `apps/web/src/i18n/errors.ts`

The twin of §10.1, one level up: `validation.ts` localizes **field** errors,
`errors.ts` localizes **request** errors — the `{ code, message }` an API failure
carries, which almost always ends up in a toast.

**Branch on the CODE, never on the message.** `error.code` is stable machine
surface (`WIP_LIMIT_EXCEEDED`); `error.message` is English prose written for a log
line. Codes are looked up **lower-cased**: the API spells them SCREAMING_SNAKE and
the catalog spells them snake_case, so one normalization here beats a convention
every call site has to remember. The ladder is **catalog entry → server message →
generic**:

```ts
apiErrorMessage(t, error); // pure; for zustand actions and catch blocks
useApiErrorMessage(); // stable (error) => string
useApiErrorToast(); // stable onError that raises a destructive toast
```

- Not an `ApiError` at all (a `TypeError` from a bad render) → `errors:unknown`.
  A stack-shaped `Error.message` is our bug, not the server's, and must not leak.
- `NETWORK_ERROR_CODE` → `errors:network_error`, mapped explicitly because "could
  not reach the server" is advice, not an error report.
- Miss detection relies on **i18next returning the key itself** when nothing
  matched (`returnNull: false`, no `parseMissingKeyHandler`) — hence
  `translated !== key` rather than `i18n.exists()`.
- Unmapped code with a message → **the server's own words**. Across five waves of
  parallel work an unmapped code is a certainty, and a toast reading "Something
  went wrong" for a failure the server explained precisely is worse than a
  sentence in the wrong language. The `errors` catalog is expected to grow.

`apps/web/src/i18n/errors.test.ts` pins all five rungs. Project checklist §B —
"toast on every mutation failure" — is satisfied by passing `useApiErrorToast()`
straight into `useMutation({ mutationFn, onError })`.

## 11. Recipe: adding a translated string

The short version is [`.agents/workflows/add-translated-string.md`](../workflows/add-translated-string.md).
The full procedure:

1. **Pick the namespace** (§2.3) — the surface the string belongs to. `common`
   only if three or more surfaces share it. Task types and priorities are
   **already** in `common:taskType` / `common:priority`, read through
   `useTaskVocabulary()`; do not re-add them to a view namespace.
2. **Choose a key that describes the MEANING, not the text.**
   `board:column.wipExceeded`, not `board:redWarning`. camelCase, nested
   `page.section.element`.
3. **Add it to `apps/web/src/locales/en/<ns>.ts`.** English defines the shape, so
   this step is what makes the key exist for TypeScript.
4. **Add the same key to `apps/web/src/locales/ar/<ns>.ts`**, using the glossary
   in §3. Do not leave it out: the parity test fails on a missing Arabic key, and
   an English string in an Arabic namespace fails the "no English string sitting
   in the Arabic catalog" check.
5. **Use it:**

   ```tsx
   const { t } = useTranslation(['board', 'common']);
   … t('board:column.wipExceeded', { limit })
   ```

   The **array** form is what enables the `ns:key` prefix in the types (§2.4).
   Outside React, import the instance: `i18n.t('diagnostics:logs.unavailable')` —
   see `stores/useDiagLogsStore.ts`, the app's one such call site.

6. **Counts:** if you need a real plural, declare `_one` + `_other` in English and
   **all six** Arabic categories, and call with `{ count }` (§4). In `board`,
   `backlog`, `roadmap` and `notifications`, use a labelled figure instead (§4.3).
   Never concatenate fragments — one key, one sentence, interpolation for the
   variables.
7. **Check it in Arabic.** Switch the language in the Topbar and look: is the
   spacing `ps-`/`pe-`? Do icons and chevrons sit on the reading side? Are digits
   Western? Does a user-typed value need `dir="auto"` (§8)?
8. **Run the guards:**

   ```
   pnpm --filter @flowboard/web test -- src/i18n
   pnpm --filter @flowboard/web typecheck
   ```

   `locales.test.ts` is the parity gate; a wrong key name is a compile error.

### 11.1 The module-scope trap

**`t()` must run at render time or later, never at module evaluation.**

```ts
// WRONG. Evaluated once, at import, in whatever language booted.
const STATUS_LABEL = { done: i18n.t('workflow:categories.done'), … };
```

The module is imported during boot, `t()` runs immediately, and the record holds
those strings for the life of the tab. Switch to Arabic and every consumer keeps
rendering English — invisible to an English-only reviewer.

**Today this codebase is clean.** The one non-test `i18n.t()` outside a component
sits inside a function body — `stores/useDiagLogsStore.ts` sets
`{ error: i18n.t('diagnostics:logs.unavailable') }` in an action, re-evaluated
per call. Keep it that way: if you need a key-to-label map at module scope, store
the **keys** and resolve them at the render site, the pattern
`components/theme/theme-presets.ts` already uses with `labelKey`.

### 11.2 Changing an existing English value

**Changing English copy is a product change, not a translation change** — English
values are read by e2e locators and static-render assertions, so an edit can
break a `getByText` or a `getByRole({ name })`. Adding a key is free; editing one
is not. Changing a `VM_*` value in `packages/shared` is stricter still: a
wire-contract change that breaks the API's 422 assertions **and** the map key in
`i18n/validation.ts` — which is the point, since it fails to compile rather than
leaking English.
